# Blender operating boundaries

Read this before a skill launches a helper, changes Blender, captures editor pixels, or changes an example `.blend`.

- Use the existing official Blender Lab MCP connection where it can do the work. Confirm read-only access before mutations, preserve unrelated scene content, use a named owned collection/run, and checkpoint before destructive edits. Report an MCP blocker instead of switching servers or starting paid services.
- On Windows, every auxiliary process in the full launch chain must be created without a console window, including brief flashes. A background Blender flag, absolute executable path, `cmd /c`, or hidden-window style does not establish that guarantee. Capture diagnostics, bound execution, and clean up owned descendants. If any boundary is unverified, do not launch; report **Blocked**, explain why, and continue safe independent work. Never use a visible terminal, system console, or window manipulation as a fallback.
- Before every Blender editor/window/area screenshot, freshly verify that the relevant editor is visible and not minimized. It may remain behind other apps; never restore, focus, foreground, minimize, maximize, or close the user's editor. If Blender is closed, ask the user to open it. If it is hidden or minimized, say **Restore Blender from the taskbar**. Inspect the captured pixels and report black or stale captures; a saved render is not editor evidence.
- When adding or changing an example `.blend`, read [the model-delivery contract](../../../../documentation/models/README.md). Keep its self-contained GLB and `.export.json` beside it, regenerate `documentation/models/index.json`, validate and browser-inspect the GLB, preserve source variants, and record actual provenance and export limitations. Do not claim public HTTP validation before publication.
